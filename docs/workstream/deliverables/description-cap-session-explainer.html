🪧 The menu board that was too small — and the inspector who kept missing it

Every skill advertises itself with a short description. Think of it as a menu board outside a shop: the board fits a fixed amount, and anything you write past the edge simply isn't there for customers to read. Earlier rounds fixed the over-full boards. This session went after something more uncomfortable — the inspector's own tools. Good outcome, and several genuinely embarrassing findings.

★ The one-paragraph version

Every model-invocable skill's description gets shown to the model on every single turn, and it's capped at 1,536 characters. Go over and the system keeps the first 1,535 and cuts mid-word — so any "use this when the user says…" phrase past that point is silently dead. Previous rounds fixed the over-full descriptions. This session was supposed to be tidy-up, and instead found that the checks meant to catch all this were themselves quietly lying: a test named "not a stale copy" passed on a genuinely stale copy; the corruption check skipped the majority of skills in one repo; and the tool that preaches "leave yourself 30–50 characters of room" had 3. All fixed, all shipped, all verified against the real installation. The honest catch: the handoff document that told me what to do opened with an instruction that was flatly false — following it would have "corrected" every published character figure across six repositories — all of which were already right.

1 What the menu board is, and why the edge matters

🪧 What goes on the board

Not marketing copy — the actual trigger phrases. "Use this when the user says budget review." If that phrase sits past the edge, the skill can no longer be summoned by it. The feature still exists; nobody can order it. And the street itself has limited frontage: when too many shops put boards out, the least-visited ones get their board removed entirely, however short it is.

📏 What the inspector does

A script measures every board, flags the ones over the edge, and lists exactly which phrases fell off. Earlier rounds used it to fix 12 over-full boards and bring back 30 dead phrases.

Engineer's note: the board is the description: field in a skill's SKILL.md frontmatter. The cap is skillListingMaxDescChars (1,536) and covers description + " - " + whenToUse as a pair; over it the harness keeps full[:1535] and appends an ellipsis. Re-extracted verbatim from the currently installed 2.1.222 binary this session — a newer build than the 2.1.221 the workstream was originally measured against. All four constants unchanged; only the minified identifiers moved.

2 The uncomfortable part: the inspector's own tools

This session's real findings. Each one is a check that ran, reported "all clear," and was believed — while not actually checking what its name claimed. Every fix below was proved by deliberately breaking it and watching it go red.

🧰A "is my tape measure current?" test that passed on a broken tape measure

Six repos keep their own copy of the inspection script. One had a test literally named "the vendored gate is current with upstream, not a stale fork." It worked by checking that three words appeared in the file. The copy was stale — and outdated in a way that made it report false alarms — but all three words were still there, because the change was inside a function whose name never changed. 284 out of 284 tests green, the whole time.

Now it compares a fingerprint of the whole file, minus its own local note. Put the old copy back and it fails, by name.

🚪The corruption check only walked the front rooms

A separate defect can scramble a description without changing its length — so no size check can see it. The inspector did look for it, but only in skills the model can summon on its own. In one repo 74 of its 94 skills weren't in that category at the time — 76 of 96 today. So for the large majority, a scrambled description was neither reported nor failed. That is exactly why four real cases there had to be found by running the tool in a different mode, rather than by the build check that was supposed to catch them.

🪞The tool that preaches "leave room" had three characters of it

Its own published rule says leave 30–50 characters spare, or your next edit breaks it. Its own board sat 3 characters from the edge — and its warning list lumped that in with boards that had 340 spare, same colour, no ordering. Retrimmed to 53 spare, and the warning list now separates the genuinely urgent.

👻A description pointing customers at a shop that doesn't exist

One description ended by redirecting the reader to a sibling skill for a related job. That skill does not exist — not in that repo, not installed, nowhere on the machine. The useful distinction it was drawing is kept; the dead name is gone. Board shrank 1,465 → 1,423, and the trigger-phrase check reported nothing lost — which, as the next finding shows, is weaker evidence than it sounds, so the removal was confirmed by hand as well.

🕶️The phrase-checker can't see half the phrases

The tool that answers "did this edit drop any trigger phrases?" only recognises phrases written in double quotes. Phrases written in backticks — error messages, flags, file paths — are invisible to it. An earlier trim in another repo removed three backticked error strings from a description and the checker cheerfully reported nothing dropped. That tool's instructions now say so, and ship a hand-run recipe that catches them — the automated check still can't see them.

📋A test that wrote its own answer sheet

A snapshot test compares output against a saved copy. For one case the saved copy had never been committed — so the test hit its "file missing, I'll create it" branch, wrote the file, and asserted literally nothing. It had been reported as a passing test the entire time. Rename a section inside that case and, before, the suite was 499 green; now it is 498 passing, 1 failing — and the one failure is the snapshot test, by name.

🔢Published numbers that its own tool disagrees with

A results table claimed "13 better / 25 unchanged / 1 marginally lower." Re-running the measuring script that now ships in that repo gives 12 better / 27 unchanged / 0 worse — the "1 marginally lower" row doesn't exist. Direction and size held up; the specifics didn't. Corrected in place with a visible note rather than quietly overwritten.

3 The finding I'd most like to have not found

📕The handbook's page 1 was wrong — and would have done real damage

The handoff document I was told to execute opened with: re-copy the script everywhere, because the new version fixed an off-by-one, so every "characters discarded" number now published is one too low.

It wasn't. One command comparing the two versions shows the only change was elsewhere entirely; the arithmetic in question had been correct in the previous version, and every copy already had it. Had I followed the instruction as written, I'd have gone through the six repositories that keep a copy of the script and "corrected" every published character figure in them — all of which were already right. That would have introduced exactly the kind of error the whole project exists to eliminate. how many figures: not counted — the handoff said "dozens" and I did not verify that word

Why it happened: the handoff was written by the session that did the work, from memory of why a version was cut, not from the change itself. Its own advice — verify nothing you have not run a command to confirm — applied to itself. A handoff is the one document nobody re-audits, because it reads as the authority.

Engineer's note: git diff 4dc1a62 HEAD -- scripts/check_skill_descriptions.py touches only find_wrap_corruption(). desc_chars - (MAX_DESC_CHARS - 1) was already present in v2.2.0, and grep -c returned 4 in every vendored copy before re-vendoring. The claim is struck in the handoff and restated in the commit bodies of the six round-3 changes that had inherited it.

⚖︎ Being straight with you (the limits)

🔁The failure this report describes happened again — to me, in this session

One of my own changes removed dead cross-references from six shipped files and bumped no version. claude plugin update compares versions, saw them equal, and did nothing — so 12 of the 32 removals were fixed in the repository and still live for an installed user. My commit message even asserted the opposite: "nothing under a plugin source dir changed."

Nothing caught it. The live-install check measures board sizes and scrambling, not whether the installed copy matches the repository — it cannot see this class of failure at all. It was found by the fact-check on this report, after I had already told you the session was delivered. Now bumped, shipped and re-verified: repository and installed copies are byte-identical for all six files, and a scoped re-scan finds 0 stranded removals. A second instance turned up in the same sweep — a dead name in another description — and is also shipped.

The honest read: the count of things I found is not evidence that I found all of them.

  • Under the cap does not mean visible — this is the big one. A second, shared limit collapses descriptions to a bare name when the whole catalogue is too big, and it drops the least-used skills first, not the longest. Measured on this machine just now: the catalogue needs 90,422 characters against a 40,000 budget even at a 1M-token context, so only about 42% of descriptions survive — the rest show as names only. At the 200k default it is far worse. Fixing the boards was necessary; it was never sufficient, and no count in this report should be read as "all these triggers are now working."
  • Five boards are still nearly full — between 23 and 39 characters spare. None is broken. Each is one edit from breaking. The tool now lists them separately instead of hiding them among boards with ten times the room, but nobody has trimmed them yet.
  • I deliberately left about eleven dead cross-references in place. I removed 32 that I checked one by one. An automated sweep for the rest deleted references to a repository, a cloud service and a session label — none of which were skills — so I threw that pass away rather than trust it. The remainder need a human eye; several are real links to things that do exist elsewhere.
  • 1,536 is a default, not a law. It is a setting: a Claude Code release, or a line in your own settings.json, can change it. Every character figure in this report is conditional on it — I re-read it from the currently installed binary, which is the best I can do, not a guarantee it holds tomorrow.
  • The phrase-checker has a second blind spot I did not fix. Beyond backticks: it compares word sets, so rewriting "fires on X — separately, watch for Y" into "fires on X whose Y" scores identically while quietly narrowing the trigger to people who already diagnosed Y. No tool here catches that; it needs a human reading the diff.
  • The five nearly-full boards aren't the whole warning list — 24 more sit above 75% of the cap with more room to spare. None is at risk today.
  • One check is stricter than it was, and nothing has hit it yet. The corruption check now covers every skill. I verified all seven repositories were clean before tightening it, so nothing broke on merge — but a repository with a pre-existing problem will now fail. The gate's own code comment records why the old scoping let four real cases sit unseen, and the re-copied file's header warns that a red build here means the problem was always there.
  • Several figures here are inherited rather than re-measured by me: the "12 over cap / 30 dead phrases" starting point and the "~41% survive" precedent come from the previous session's write-up; "74 of 94", "340 characters spare" and "four real corruptions" come from this session's commit messages. Everything in the tiles and the regression table I re-ran today.
